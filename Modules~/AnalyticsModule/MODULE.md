# Analytics

## Purpose
Takes an analytics event - a name and its parameters - from any module through `IAnalyticsService`
and hands it to every SDK plugged into its socket, queueing for one that is still coming up; the
game never learns which SDKs those are.

## Concepts
analytics, event, log event, track, tracking, user property, user id, consent, provider, plug,
socket, Firebase, Facebook, funnel, IAnalyticsService, IAnalyticsProvider, AnalyticsEventVO

## Using it
1. `AnalyticsServiceRoot` into the scene the game boots from, Initialize Order -85.
2. The SDKs the game wants, their own setup done, and their define where the plug's card says so.
3. On the Root, Add Sub Context: `FirebaseAnalyticsServiceContext`, `FacebookAnalyticsServiceContext`,
   or the game's own `[AllowAsSubContext]` context that plugs its own `IAnalyticsProvider` - and
   leave **AutoSetup** on each entry (Add Sub Context ticks it), or its Setup never runs and
   nothing is plugged.
4. Event names as constants in the module that logs them, and the logging as a step of that
   module's sequence. A fixed event is one bound line:
   `.ToSequence<IAnalyticsService.Commands.Log>(new AnalyticsEventVO("settings_opened"))`. An
   event with a value from the payload or the model is a game Command injecting
   `IAnalyticsService`: `_analytics.Log(new AnalyticsEventVO("level_start").With("level", level))`.
   Nothing in the Connector.
5. One `SetConsent` from wherever consent is resolved, `SetUserId` once the player is known,
   `SetUserProperty` for what the dashboards segment on - the A/B group, the player level.

## Decisions
- **A Service with a socket, not a listener.** HitNPoP's analytics module bound the signal holders
  of 27 other modules and wired them in its own Setup, so it was the one thing in the project that
  knew everything. Here events reach the module through `IAnalyticsService` from the module that
  decided them, and never through a lambda in a Connector.
- **One `IAnalyticsProvider` per SDK, plugged by a hosted context.** A provider is a class behind
  the socket and a `[AllowAsSubContext]` context that plugs it in Setup; the Root's Sub Context
  Types list is the socket strip. A ScriptableObject on the adapter or a component under the Root
  would have done the same job with a list of its own; the sub-context list already has AutoSetup,
  IsTest, a MonoScript reference that survives a rename, and a module that installs and publishes
  with its parent.
- **Providers ship under `zSubModules/` and compile only under a define.** The core references no
  SDK; each plug's assembly carries a define constraint that a version define sets for a UPM SDK
  (Firebase) and the developer sets for a `.unitypackage` one (Facebook).
- **Queue per slot, current values in the model.** Events wait per provider until that provider
  is ready, capped at 200 with the oldest dropped and the count reported once. Consent, the user
  id and the user properties are current values: a slot that becomes ready reads them at its
  flush - consent first, because Firebase wants it before the first event - and a slot already
  ready receives each change as it comes.
- **Providers plug in Setup, the service initializes in Launch.** Every Setup in the scene runs
  before any Launch, so every plug listed on the Root has plugged by then. A provider plugged
  later is initialized at once and sees events from then on.
- **Consent handed on, never resolved.** `AnalyticsConsentVO` is Google Consent Mode's four flags;
  the consent form and the ATT prompt are another module's.
- **No `Scripts/Signals`, no `Scripts/Shared`, no asset, no event vocabulary.** The interface is
  the whole surface; the queue absorbs the only wait; a game keeps its names beside its Commands.
- **Order -85.** After the two data seats, before every service that might log; not on a ten
  because every ten is taken, and only reading order depends on it.

## Known gaps
- The Firebase and Facebook plugs are not compiled in this project (no SDK here); both compiled
  clean in FlowIoC-local-test against the SDK DLLs on 2026-09-16, and neither has run on a phone yet.
- No timeout on a provider's Initialize: an SDK that never answers keeps its slot Initializing and
  its queue at the cap, with nothing reported after the first drop line.
- No typed helpers for purchase, ad revenue or progression events.
- No panel; the test scene's label is the one view of the slots.
- Consent is not remembered across sessions; the game's consent flow re-applies it at boot.
